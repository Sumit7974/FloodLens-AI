1. Project vision, scope and product boundaries
1.1 Product outcome
FloodLens AI connects three phases: (1) Predict & Protect before a flood, (2) Detect & Respond during/after the event,
and (3) Evaluate & Improve from verified observations. It serves two audiences via one shared backend: authorities
receive geospatial and response controls on a web dashboard; citizens receive location-specific information, test
alerts, destinations and assistance workflows on Android.


1.2 Assigned problem statement - non-negotiable
• Compare suitable pre-flood and post-flood optical satellite imagery of a Nepal Terai river sector (Sentinel-2 or Landsat 8/9).

• Detect newly flooded areas using spectral water indices such as NDWI or MNDWI, with cloud masking and geospatial
alignment.

• Produce a raster or vector flood-extent map and an affected-settlement report for at least one real test scene.

• Evaluate detection against a credible reference mask where available; assess settlement-impact flags and visualization
clarity.



1.3 Version 1 delivery tiers

                                                                  dashboard; Android risk/alerts/help; basic risk prototype; WebSocket

  B: Conditional           Integrate only after dataset and       Sentinel-1 radar; verified shelters/hospitals; tested candidate routing; 3D
                           core readiness are proven              terrain; depth scenario output; multi-channel message tests; offline model
                                                                  retraining.

   Important scope distinction
   All five advanced features remain in the overall design and may have demonstrable V1 slices: 3D terrain,
   inundation-depth modelling, Sentinel-1 radar, multi-channel alerts and candidate retraining. They must never
   compromise the optical mapping deliverable or be presented as fully validated when they are not.



1.4 Success story
Historical replay: a region receives a +3h elevated-risk estimate; an authority reviews a test warning; a citizen Android
device receives it; later optical satellite processing produces a real flood extent map; the system flags
settlement/asset intersections and citizen test requests; the analytics screen compares the saved risk estimate with
valid later observations and records errors.

4. AI, hydrology and satellite processing specification
4.1 Prediction - baseline before advanced ML
Define a spatial prediction unit (e.g. settlement polygon or grid cell) and target label (flood/no flood over next 1h, 3h or
6h). The first risk baseline should be interpretable and use only inputs known at issuance time. Candidate features
include accumulated/forecast rainfall, upstream water-level trend, discharge when available, river proximity, terrain
elevation/slope, historical inundation and verified dam-release timing.

• Record issued_at and target_valid_at separately; one forecast run contains three horizon outputs.

• Train/test split by historical event and time; never randomly split adjacent pixels as if fully independent.

• Use missingness flags; unavailable river/dam readings are not silently treated as zero.

• If labels allow, evaluate precision, recall, false alert rate, Brier score and probability calibration per horizon.

• If hourly truth is missing, report the inability to validate +1h/+3h/+6h outcomes independently.



4.2 Optical flood-mapping pipeline - mandatory

  Stage         Operation                                                          Quality check


  1             Select pre/post images, common AOI and equal analysis              Acquisition dates, cloud cover and event relevance
                resolution                                                         verified.


  2             Cloud/shadow mask, resample/reproject and align bands              No invalid pixels incorrectly classified as dry land.


  3             Compute NDWI = (Green-NIR)/(Green+NIR), optionally MNDWI           Band names and dynamic thresholds documented.


  4             Build pre/post water masks; exclude permanent water where          Image artifacts and seasonal water changes noted.
                suitable


  5             Compute newly inundated pixels and clean speckle                   No removal of meaningful small flooded settlements.
                conservatively


  6             Export GeoTIFF and GeoJSON with CRS/source metadata                Flooded area km2 consistent with pixel geometry.


  7             Intersect extents with settlements/assets                          Spatial join tested against manual sample cases.


  8             Compare against reference mask if available                        Report IoU, precision, recall and coverage limitations.




4.3 Radar / depth / 3D extensions
• Sentinel-1 SAR: Pre/post backscatter-based water-change analysis with sensor geometry controls; preserve separate output
and validation, never silently replace required optical output.

• Depth modelling: Requires a physically defensible water-surface/hydrodynamic method and uncertainty range. DEM is ground
elevation, not observed water depth. If unsupported, show relative terrain/qualitative exposure only.

• 3D web: CesiumJS terrain and layers, with clear altitude units, vertical datum assumptions, 2D toggle and time selector.
Mobile defaults to readable 2D, with optional 3D on capable devices.

• Asset impact: Use polygon intersections to calculate potential exposure. Do not equate polygon overlap with confirmed
destruction or injury.

6.2 API conventions
• Prefix /api/v1; response dates in UTC ISO-8601; WGS84 GeoJSON at REST boundary; standardized pagination and filtering.

• JWT or secure session authentication; role and geographic scope checked on every sensitive operation.

• Errors use {code, message, request_id, details?}; HTTP status correctly reflects error.

• Mutations affecting alerts or assistance emit auditable records; sensitive create actions support idempotency keys.

• Large tile/raster files retrieved by signed object URLs or secured map tile endpoint, not inside JSON or WebSockets.

• Transaction order: commit database state -> persist event/outbox -> distribute WebSocket message -> clients fetch

10.2 Failure and regression scenarios
• Offline phone or broken WebSocket; state refresh after reconnection and no duplicate assistance submission.

• No post-event optical scene or heavy cloud mask; report data unavailable rather than invent water.

• Invalid location, role mismatch, absent notification permission, failed messaging channel, stale sensor.

• Malformed coordinates, incorrect CRS, mismatched raster resolution, empty settlement layer.

• Two identical help requests retried, two authorities updating same case, accidental duplicate alert send.

• Reprocessing same satellite scene produces traceable job/version and does not overwrite history incorrectly.

10.3 Measurable evaluation
Flood detection: Intersection-over-Union, precision and recall, computed against an independent pixel/region reference
when available. Settlement correctness: confusion count or precision/recall over verified settlement flags. Forecast
performance: separate per-horizon confusion metrics and calibration only where properly timed truth exists. No single
unsupported "overall accuracy" score.
