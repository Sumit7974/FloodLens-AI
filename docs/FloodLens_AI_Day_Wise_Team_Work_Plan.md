 01 | Roles, priorities and daily rules
 Each developer owns one primary area. Integration and testing remain shared responsibilities. The
 backend lead coordinates interfaces, but does not become the only person fixing cross-team issues.


   Member              Primary ownership                            Integration support


   Member 1 (you)      FastAPI backend, PostGIS, REST APIs,         Web dashboard APIs and end-to-end integration
                       WebSockets, authentication, alert and
                       assistance workflows


   Member 2            Sentinel-2 optical mapping, Sentinel-1       Expose geospatial files/layers to the backend
                       radar, GIS layers, settlement exposure, 3D
                       terrain


   Member 3            +1h/+3h/+6h risk baseline, hydrological      Risk/exposure logic, citizen risk APIs
                       inputs, depth-model research, performance
                       evaluation


   Member 4            React authority dashboard, React             UI integrations and Android build
                       Native/Expo Android, screen navigation and
                       notifications



 Feature priorities
 P0 — mandatory: Optical water-index detection, flood extent, affected settlements, reference-mask accuracy
 checks, impact report.

 P1 — core experience: Risk forecast prototype, web + Android apps, approved test alerts, assistance requests,
 WebSockets, prediction comparison.

 P2 — advanced: 3D terrain, radar, depth modelling, verified shelters/hospitals, candidate routes, multichannel
 adapters.

 P3 — experimental: Offline candidate retraining, uncertain flood-depth results, broader live integrations. Never
 block P0/P1.



   Daily integration rules
   Morning: 15-minute status and blockers. Midday: interface check. Evening: tested merge, smoke test and
   20-minute demo review. Use feature branches, shared schemas, UTC timestamps and reproducible demo
   data.

 DAY 01 | Foundation, datasets and
 application skeletons
 Day goal: Everyone can run the code and critical datasets are confirmed.


     MEMBER 1 / BACKEND
     • Create repo structure and initialize FastAPI
     • Configure PostgreSQL + PostGIS and environment settings
     • Implement /health, basic auth, authority/citizen roles
     • Publish initial REST and WebSocket contracts




     MEMBER 2 / SATELLITE & GIS
     • Choose a specific historical Nepal Terai test event
     • Verify usable pre/post Sentinel-2 optical scenes
     • Check Sentinel-1 radar and DEM availability
     • Collect settlement, road, building and facility layers




     MEMBER 3 / AI/ML
     • Audit historical forecast, river and dam inputs
     • Define risk labels, locations and +1h/+3h/+6h horizons
     • Build data-cleaning script and simple reproducible baseline
     • Record missing feeds, model limitations and test requirements




     MEMBER 4 / WEB & ANDROID
     • Initialize React web and Expo Android projects
     • Build navigation, shared visual components and screen shells
     • Create authority overview and citizen home layouts
     • Connect both apps to /health and mock forecast endpoint




   End-of-day deliverable
   Both app skeletons start; backend/db health check passes; one real flood event and usable optical imagery
   are confirmed.


 Fallback / decision gate: Change the study area immediately if appropriate optical scenes or settlement data are missing.

 DAY 02 | Optical flood mapping and
 prediction baseline
 Day goal: Meet the required satellite-mapping core before expanding.


     MEMBER 1 / BACKEND

     • Implement prediction, settlement and map-layer responses
     • Store GeoJSON/flood layer references and metadata

     • Cloud-mask and align before/after optical imagery
     • Run NDWI/MNDWI and extract newly flooded pixels

     MEMBER 3 / AI/ML
     • Implement baseline +1h/+3h/+6h risk outputs
     • Process available weather and hydrological inputs
     • Create area-level risk classifications with timestamps
     • Check which historical outcomes permit fair evaluation




     MEMBER 4 / WEB & ANDROID
     • Build authority command and satellite map screens
     • Create before/after imagery comparison UI
     • Build Android risk, forecasts and local map screens
     • Connect both apps to forecast/flood extent endpoints




   End-of-day deliverable
   Real optical flood map, initial settlement flags, runnable risk baseline and visible results in both clients.


 Fallback / decision gate: Suspend advanced radar, depth and 3D work if flood extent or settlement intersection is not

 Acceptance criteria and handoff checklist
 Use this checklist at the daily merge review and at the Day 5 feature freeze. The team should be
 able to reproduce each result, not merely display screenshots.


 Tier         Test / evidence


 P0           Optical pre/post flood imagery processed with NDWI/MNDWI and cloud checks


 P0           Georeferenced flood map produced and settlement impacts calculated


 P0           Flood extent and impact report export works; reference accuracy reported if available


 P1           +1h/+3h/+6h risk baseline returns traceable timestamped results


 P1           Authority web and citizen Android both access real backend records


 P1           WebSocket updates recover after lost connections


 P1           Authority-approved test alert is received on Android


 P1           Citizen request can be submitted and its status updated by authority


 P1           Historical prediction vs observation results explain valid comparisons and gaps


 P2           3D terrain and radar results load where supported


 P2           Shelter/hospital and route displays indicate verified status and time freshness


 P3           Offline model candidate comparison documented; no unattended deployment



 Final risk and fallback rules
 • If satellite images are unusable, switch historical event/scene on Day 1; never invent a map.

 • If hourly flood labels are unavailable, show risk baseline and disclose that accuracy is not validated.

 • If radar, depth, 3D or routing are unstable, retain tested 2D optical detection and clear limitations.

 • If external APIs fail during judging, switch to a locally cached, timestamped historical replay.

 • If FCM/SMS/WhatsApp access is unavailable, demonstrate authorized in-app alerts and recorded event history.

 • After Day 5, fix critical issues only; do not broaden scope.



   The one non-negotiable milestone
   By Day 2 we must have an authentic optical flood extent map and affected-settlement analysis. It directly
   solves the assigned Nakshatra problem statement; all other innovations should build on top of this
   foundation.
