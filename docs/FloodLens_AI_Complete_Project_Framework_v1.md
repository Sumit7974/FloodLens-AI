 1. Product Vision and Scope
 Core question: When and where could flooding occur, how can communities prepare, where has flooding
 actually occurred, what assets may be affected, who needs assistance, and how can future forecasts improve?

 FloodLens AI will serve two user groups: authorities requiring detailed situational awareness and citizens
 requiring concise location-based warnings and guidance. Both interfaces will use a common backend and share
 consistent incident, prediction and observed-map data.


  PHASE                    PURPOSE                                   KEY OUTPUTS


  1 - Predict & Protect    Before flood: estimate risk and support   +1h/+3h/+6h risk; risk map; exposed assets; reviewed alerts;
                           preparedness                              shelter/route information


  2 - Detect & Respond     During/after flood: map observed          Optical imagery analysis; flood mask; affected settlements;
                           extent and respond                        report; citizen requests


  3 - Analyze & Improve    After flood: measure errors and           Archived forecasts; observed comparison; metrics; candidate
                           validate model updates                    model evaluation




 Mandatory alignment with Nakshatra problem statement
 For at least one Nepal Terai historical test scene, demonstrate pre/post optical satellite comparison, water
 detection using a spectral index such as NDWI/MNDWI, georeferenced newly flooded extent,
 affected-settlement assessment, visualization, and an impact report. Reference-mask testing should be
 included when an adequate reference is available.


  Non-negotiable distinction: predicted flood risk, satellite-observed inundation, modelled floodwater depth and confirmed
  physical damage are different outputs. Label each clearly; never present unverified depth or infrastructure loss as observed
  fact.




 2. Full Technical Architecture
 Layer 1 - Data ingestion: weather predictions, available river gauge readings/discharge, dam release bulletins,
 terrain DEM, historical flood events, satellite imagery, settlements, buildings, roads, verified hospitals and
 shelters.

 Layer 2 - Intelligence services: three-horizon risk baseline, optional ML model, optical water detection,
 radar/SAR extension, inundation-depth model, exposure analysis and geospatial quality checks.

 Layer 3 - Decision support: risk classification, transparent priority explanations, known road-hazard checks,
 reviewed alert proposals, shelter discovery and assistance request triage.

 Layer 4 - Core backend: FastAPI modular monolith, relational geospatial storage, REST APIs, event log, secure
 user roles, authenticated WebSocket updates and background processing jobs.

 Layer 5 - Applications: authority web dashboard (React) and citizen Android app (React Native/Expo).

 Layer 6 - Evaluation: stored predictions/observations, reference accuracy metrics, historical replay, error
 review, candidate retraining and human model-approval gate.

 4. Phase 2 - Detect & Respond (Assigned PS)
 4.1 Optical satellite detection pipeline
 Before image -> Cloud/quality mask -> Water index -> Baseline water mask -> After image -> Water index ->
 Post-event water mask -> Newly inundated pixels -> Georeferenced flood map.

 4.2 Settlement, asset and severity assessment

 4.3 Citizens and authorities during the event
 Citizens can submit geolocated assistance requests and review their own request status. Authorized authorities
 can triage, update and audit these reports. A WebSocket event notifies connected dashboards of a new request,
 but the original record is stored durably in the database.


  Evidence boundary: a flood polygon indicates mapped water coverage, not automatically destroyed buildings, injuries or
  people needing rescue. Mark any unverified damage or rescue estimates as potential exposure and require field confirmation.




 5. Phase 3 - Analyze & Improve
 Every forecast run stores the prediction creation time, applicable horizon, model version, input data versions
 and geographical extent. Later observations are matched only when times and locations support a valid
 comparison.


  MODULE                               BEHAVIOUR


  Forecast archive                     Immutable saved estimates for +1h/+3h/+6h and related inputs.


  Observation matching                 Compare only with sufficiently time-aligned and reliable ground truth.


  Error analysis                       Report missed events, false alarms, spatial errors and uncertainty; distinguish map quality from
                                       forecast skill.


  Candidate model training             Offline retraining from verified examples if enough labelled data is available.


  Independent evaluation               Compare baseline and candidate on untouched historical events; check calibration and
                                       regression risk.


  Human approval                       Never deploy a newly trained model automatically without a quality and safety check.


 Proof in the hackathon: demonstrate saved prediction vs later evidence, explain limitations, and optionally
 present a baseline-versus-candidate model experiment. Self-retraining is a roadmap capability, not a claim that
 every new flood automatically makes predictions more accurate.

 10. Scope Priorities and Feasibility

  DELIVERY LEVEL                     INCLUDED FEATURES


  Core - must demonstrate            Optical flood map, settlements, report and accuracy; basic +1/+3/+6 risk; authority web; citizen
                                     Android; test alerts; assistance requests; prediction-observation review; APIs/WebSockets.


  Advanced, data-dependent           3D terrain on both surfaces; depth-model demonstration; Sentinel-1 radar; verified
                                     shelters/hospitals and candidate routing; SMS/WhatsApp test adapters; candidate retraining.


  Excluded as production claims      Guaranteed hourly flood forecasts, guaranteed flood depths or evacuation routes, confirmed
                                     satellite-only property damage, unsupervised model deployment, autonomous rescue allocation,
                                     unapproved real public warning broadcasts.




 Advanced-feature feasibility gates
 3D: keep only if it renders smoothly and maps line up correctly. Depth: publish actual numbers only with
 reasonable hydraulic inputs and a documented method. Radar: use after an optical flood map is proven.
 Messaging: activate extra channels only with test-verified provider access. Retraining: demonstrate offline only
 with enough independent examples.


  Project management principle: all requested advanced capabilities remain in the architecture for both applications where
  appropriate. However, they must not delay or compromise verified satellite mapping and a stable end-to-end demo. A
  prototype is not an operational flood safety product.

 13. Demo Sequence and Operational Safeguards
 Demo sequence: Open a historical event -> display a timestamped +3h risk estimate -> review and approve a
 test alert -> receive it on Android -> show candidate shelter/route where data permits -> display real optical
 flood detection and affected villages -> submit and review a demo assistance request -> compare prediction
 with valid later evidence -> inspect candidate model results if available.

 Safeguards: keep hypothetical/mock events separate from actual data; avoid public broadcasts; restrict
 individual location data; timestamp every hazard map; require human review for emergency decisions;
 preserve historical prediction versions; provide no-guarantee warnings for route and depth estimates.

 Recommended opening pitch: "FloodLens AI connects three stages of disaster intelligence: preparing for flood
 risk before the event, mapping observed inundation and potential impacts during the event, and learning from
 verified outcomes to improve future forecasts."
