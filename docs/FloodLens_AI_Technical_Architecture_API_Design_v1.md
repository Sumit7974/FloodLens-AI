 1.1 Application boundaries
 • Authority web: Full monitoring, pre/post imagery, flood extent, 3D layers, impact assessment, response review,
 alert approval, analytics, model comparison and reports.

 • Citizen Android: My Area, three-horizon risk, local hazard maps, alerts, verified shelters/hospitals, route
 candidate viewing, help requests and request status.

 • Shared backend: Prediction, scene processing, GIS analysis, route assessment, record storage, authorization
 and communication. Mobile devices do not train models or process raw satellite rasters.

 2.1 Phase 1: Predict & Protect
 Inputs are cleaned and mapped to common spatial units. Each prediction run produces a unique ID, issue
 timestamp, horizon, model version, risk category, data-quality status and optionally a validated probability. The
 output can be overlaid with settlements/assets to flag potential exposure. Alert rules generate an internal
 proposal for authorized review.


 2.2 Phase 2: Detect & Respond
 Acquire pre- and post-event optical scenes; mask clouds, align imagery and compute a spectral water index
 (NDWI/MNDWI). Compare water masks to estimate newly flooded locations, convert to georeferenced
 raster/vector layers, intersect with settlements/assets, and export a map and impact report. Where a trustworthy
 reference mask exists, evaluate IoU, precision and recall. Sentinel-1 SAR provides an optional complementary
 layer.


 2.3 Phase 3: Analyze & Improve
 Compare forecasts issued before an event with appropriately timed observations. Preserve false alarms, missed
 areas, model/data limitations and outcomes. If enough verified historical examples exist, train a candidate offline
 and test against untouched events; require explicit approval before deployment. A delayed satellite image alone
 cannot prove exact +1h or +3h timing.

 3.2 Data rules
 • Use PostGIS geometry types and spatial indexes; agree on a standard CRS for storage, with explicit reprojection
 for raster operations.

 • Every derived layer references its source scene(s), processing version and creation timestamp.

 • Keep citizen help-request locations restricted to authorized responders; do not broadcast personal details
 through public channels.

 • Large imagery, rasters, report files and tiles are stored separately; the database stores secure references and
 metadata.



 4. REST API surface
 Base path: /api/v1. Private endpoints require authentication, and authority-only mutations must check role and
 geographical scope. The following routes are an initial interface contract; parameter and response schemas are to
 be frozen before parallel implementation.

 5.2 Common response expectations
 • Required keys: resource ID, location/event association, generated/observed timestamp, source or model
 version, status, mode and data-quality flags.

 • The server returns actionable missing-data or failure status, never fake zero-valued observations.

 • Event and layer IDs should be stable; web and Android consume the same API contracts.



 6. WebSocket and push communication
 WebSocket path: /ws/v1/events. Authenticate each connection, authorize subscriptions by role/location and send
 lightweight change notifications. Detailed data is fetched using REST. Example event:

  {
   "event_id": "evt_1007",
   "type": "risk.updated",
   "timestamp": "2026-10-17T06:10:00Z",
   "location_id": "village_demo_01",
   "resource_id": "fc_demo_001",
   "version": 2
  }


 6.1 Event catalogue

   Event type                                       Meaning


   risk.updated                                     New forecast published


   sensor.updated                                   New observation ingested


   flood_extent.updated                             Processing completed and extent changed


   alert.approved                                   Authorized approval recorded


   alert.published                                  Approved warning visible


   assistance.created                               New permitted request for responder dashboard


   assistance.updated                               A request changed status


   processing.completed                             GIS/analysis/background job complete




 6.2 Real-time reliability policy
 • Record the state change in the database before publishing the event. Use transaction/outbox pattern when
 more than one worker is deployed.

 • Send only minimal, non-sensitive IDs in public/location channels; citizen-specific events require verified
 ownership.

 • Reconnect with backoff, then refetch current state via REST; do not rely on receipt of every WebSocket
 message.

 8. Security, privacy and failure handling
   Scenario                                  Required system behavior


   Sensor API unavailable                    Keep last timestamped observation; mark stale; do not invent readings


   Satellite processing fails                Mark job failed; keep prior verified layer intact; log reason


   Forecast model cannot run                 Fallback to transparent baseline or unavailable state, never invented scores


   WebSocket disconnects                     Reconnect and synchronize latest authorized state using REST


   Alert-provider failure                    Persist attempt and error; do not report delivery success


   Route data stale                          Warn that path cannot be confirmed safe; defer to official guidance


   Unauthorized access                       Deny; never leak precise citizen assistance locations


   Invalid user-submitted data               Validate, return understandable error, preserve consistent state


   Training fails or degrades                Retain current model and report candidate test result

 8.1 Essential controls
 • Role-based permissions, scoped location access, TLS/WSS transport, bounded upload sizes and API rate limits.

 • Auditable approval for alert publication and model changes; protect any records containing citizen location or

 • Explicit distinction between live observations, forecasts, historical replay and simulated/test notifications.

 10. Acceptance tests and scope boundary
   Area                                Minimum test


   Required satellite PS               Process a real optical image pair into a flood map; intersect settlements; export report


   Mapping evaluation                  Compare to trusted reference mask where available; declare dataset caveats


   Prediction                          Return reproducible +1/+3/+6 horizon results with issue time, model version and inputs


   Alert flow                          Authority creates/approves and dispatches a test warning to an authorized test recipient


   Assistance                          Android creates a test request; authority dashboard receives it and updates its status


   Web + Android sync                  Both apps show consistent persisted state after disconnect/reconnect


   3D map                              Visualize terrain and separate observed vs predicted overlays without implying depth accuracy


   Phase 3                             Compare prior forecast to suitably timed verified observations; model candidate optional


   Privacy                             Only authorized responders see individual assistance locations


   Report                              Download georeferenced flood layer and impact/limitations summary




 10.1 Explicit exclusions from a production-ready claim
 Guaranteed hourly forecast accuracy; guaranteed safe routes or open hospitals; structural damage inferred solely
 from flooded pixels; autonomous rescue dispatch; unreviewed emergency broadcasts; automatically deployed
 model updates; nationwide live coverage; and guaranteed emergency-grade availability are outside this five-day
 prototype.


   Definition of success: An evidence-backed, reproducible Nepal Terai flood
   extent/settlement assessment, visibly connected to a risk-estimation prototype, an
   authority dashboard, a citizen Android application, and a credible evaluation workflow.
